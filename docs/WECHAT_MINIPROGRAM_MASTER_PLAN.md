# 微信小程序重构总计划（Web 同步版）

## 1. 背景与目标

当前仓库同时包含 `Next.js Web` 与 `miniprogram`，但两端已出现业务漂移：

- 小程序接口约定与后端真实接口不一致（部分路径失效）。
- 小程序页面存在跳转到不存在页面、字段命名不一致、支付链路与当前后端策略不一致。
- Web 已完成“单链路登录/支付/提现”收敛，而小程序尚未对齐。

本计划目标：把当前项目交付为**可持续迭代、可联调、可发布**的微信小程序版本，而不是一次性补丁。

## 2. 约束与原则

- 复用现有后端 `src/app/api/*`，避免重造第二套后端。
- 小程序采用**原生小程序技术栈**（沿用 `miniprogram/`），先稳后快。
- 与 Web 对齐关键业务规则：
  - 登录：统一用户体系（不引入历史并行登录流）。
  - 支付：遵循后端现行策略（订单优先余额支付，充值走微信支付）。
  - 提现：统一审核链路。
- 先修基础设施与接口契约，再做页面功能扩展。

## 3. 范围定义

### 3.1 本期必须完成（P0）

1. 小程序可登录并保持会话。
2. 首页/账号详情/下单主链路可走通。
3. 订单列表与详情可用。
4. 个人中心、实名认证、钱包基础信息可用。
5. 账号发布主流程可用（与 Web 核心字段对齐）。
6. 构建、预览、上传脚本可稳定执行。

### 3.2 次优先级（P1）

1. 聊天与客服链路完善。
2. 钱包统计、账单等增强页。
3. 体验优化（骨架屏、错误提示、空状态统一）。

### 3.3 暂不纳入（P2）

1. 管理后台（继续保留 Web Admin）。
2. 非核心营销静态页全量迁移。

## 4. 迁移阶段与里程碑

## Phase 0：盘点与基线冻结（0.5 天）

产出：

- 功能矩阵（Web 功能 vs 小程序现状 vs 目标状态）。
- 接口契约清单（请求/响应字段）。
- 风险清单与发布前置条件。

验收：

- 明确 P0/P1/P2 边界。
- 明确阻塞项（如小程序登录、支付接口可用性）。

## Phase 1：基础设施与契约对齐（1~2 天）

工作项：

1. 统一小程序 API 层：
   - 修复失效路径。
   - 增补缺失方法（交易记录、用户统计聚合等）。
   - 统一 snake_case / camelCase 映射。
2. 导航与页面路由清理：
   - 清理不存在的页面跳转。
   - 修正 tabbar 路径。
3. 登录基础链路打通：
   - 增加 `/api/auth/miniprogram`（code -> openid -> token）。
   - 绑定手机号链路对齐到现有用户资料接口。
4. 钱包统计接口认证修复（与 `verifyToken` 对齐）。

验收：

- 小程序启动不报关键运行时错误。
- 登录、首页、个人中心、钱包接口全部 2xx 可返回有效业务数据。

## Phase 2：核心业务页面迁移（2~4 天）

工作项：

1. 首页：筛选、分页、账号卡片数据统一。
2. 账号详情：价格、租期、状态展示与 Web 口径一致。
3. 下单链路：创建订单、状态刷新、失败回滚提示。
4. 订单页：列表、详情、关键状态动作（验收/退款申请等）。
5. 账号发布页：字段与 Web 发布页保持一致（包含租期自定义选项）。

验收：

- “浏览账号 -> 下单 -> 订单查看”链路完整可测。
- 发布账号后可在首页/后台看到一致数据。

## Phase 3：支付与钱包完善（1~2 天）

工作项：

1. 明确订单支付策略：
   - 当前后端策略为余额支付优先，需在小程序文案与交互中体现。
2. 充值支付：
   - 对齐可用支付创建接口。
   - 拉起微信支付并处理回调后状态刷新。
3. 提现流程：
   - 提现申请、记录、详情对齐现有接口。

验收：

- 充值、提现、余额变更可闭环验证。

## Phase 4：个人中心增强与实时能力（1~2 天）

工作项：

1. 实名认证（提交/结果查询/状态展示）。
2. 聊天群组与消息页联调。
3. 客服入口统一。

验收：

- 核心个人中心操作可用，无死链。

## Phase 5：质量保障与发布（1 天）

工作项：

1. E2E 冒烟清单执行。
2. 异常场景回归（401、网络超时、空数据、支付失败）。
3. 微信开发者工具真机调试。
4. 版本号与上传说明固化。

验收：

- 通过发布检查表后上传。

## 5. 任务拆解（按模块）

- 登录认证
  - `/api/auth/miniprogram` 新增
  - token 存储与失效处理
- 账号交易
  - accounts/order 链路对齐
- 钱包
  - wallet / transactions / statistics 统一
- 个人中心
  - profile / verification / settings
- 聊天客服
  - user-groups / group messages / customer-service

## 6. 风险与应对

1. 风险：小程序登录接口缺失。
   - 应对：优先补 `auth/miniprogram`，作为全链路入口。
2. 风险：支付策略与历史小程序逻辑冲突。
   - 应对：以后端当前策略为准，先保证余额支付与充值链路。
3. 风险：接口字段不一致导致页面错乱。
   - 应对：在 `utils/api.js + transformer` 做统一字段映射。
4. 风险：旧页面死链影响验收。
   - 应对：统一路由守卫和不可用功能占位提示。

## 7. 验收标准（Definition of Done）

- 小程序可登录并稳定保活。
- 首页、详情、下单、订单、发布、钱包、个人中心可用。
- 无关键死链与阻塞级报错。
- 真机冒烟通过，具备上传发布条件。

## 8. 执行顺序（本次开始）

1. 先完成 Phase 1（基础设施与契约对齐）。
2. 再进入 Phase 2（核心页面与链路）。
3. 每个阶段完成后执行一次冒烟回归并记录。
